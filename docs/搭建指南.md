## 1. 架构总览

```
Claude Code / CC-Switch / 任意 OpenAI 客户端
        │  Anthropic 协议 /v1/messages 或 OpenAI 协议 /v1/chat/completions
        ▼
┌─────────────────────────────────────────────┐
│  Universal-AI-Gateway（单进程，单端口）        │
│  · 协议双向转译（含流式 SSE / thinking 块）    │
│  · 虚拟密钥鉴权 → 模型路由 → 候选容灾         │
│  · WorkBuddy 多账号池调度（粘性 + 轮换 + 冷却）│
│  · 401 无感续签（token 轮换写回 SQLite）      │
│  · Web 管理控制台（同端口 / 路径）            │
│  · SQLite 单文件存储（db/custom.db）          │
└─────────────────────────────────────────────┘
        │  按路由候选分发（region 正确分组）
        ├─→ copilot.tencent.com / www.codebuddy.cn   （WorkBuddy CN）
        └─→ www.codebuddy.ai / www.workbuddy.ai      （WorkBuddy INTL）
```

**关键事实**：

| 项 | 值 |
| :--- | :--- |
| 进程模型 | 单 Node.js 常驻进程，控制台与网关 API 同端口 |
| 默认端口 | 生产 `18787`（`pnpm start`）；开发 `pnpm run dev`（可用 `PORT` 覆盖） |
| 存储 | Prisma + SQLite 单文件 `db/custom.db`（账号 / 路由 / 密钥 / 日志 / 签到全在内） |
| 备份 | 整库即单文件——复制 `db/custom.db` 即完成冷备；控制台另有 JSON 一键导出 |
| 上游 | WorkBuddy（腾讯云代码助手，CN/INTL 双 region）、OpenAI 兼容、Anthropic 兼容、OpenCode Zen、Qwen 网页版 |

## 3. 安装与首次启动

### 3.1 安装与初始化

```bash
git clone <本仓库> uag && cd uag

# 1. 安装依赖
pnpm install

# 2. 生成 Prisma Client 并建库（首次必须）
pnpm run db:generate && pnpm run db:push

# 3. 启动（生产模式）
pnpm run build && pnpm start
# 或开发模式（热重载）
pnpm run dev
```

### 3.2 首次启动引导

访问 `http://127.0.0.1:18787/`：

1. 数据库无管理员时自动进入**初始化引导页**：设置管理员用户名/密码，（可选）顺手配置首个上游。
2. 完成后**一次性**展示三个自动生成的密钥——**立即保存**：
   - `master_key`（管理主密钥：`/admin/api/*` 全量操作）
   - `cron_secret`（定时任务降权密钥）
   - 默认客户端密钥 `sk-uag-…`（客户端接入用，可在控制台再生成多把）
3. 之后访问即登录页。管理员密码可在「设置」中修改（改密后全部会话失效）。

### 3.3 启动自检

```bash
curl http://127.0.0.1:18787/healthz
# {"status":"ok","service":"universal-ai-gateway","version":"3.0.9",...}
```

零提供商/零路由时返回 `503 degraded` 而非永远 ok——这是刻意设计，避免假健康。

## 4. WorkBuddy 凭证获取

WorkBuddy（腾讯云代码助手 / CodeBuddy）账号的凭证是 **OIDC 三件套**：`userId`（uid）、`accessToken`、`refreshToken`。获取途径：

### 4.1 途径 A：WorkBuddy 账号切换器导出（推荐）

使用社区账号切换器工具（导出文件名形如 `wb-switch-accounts-YYYY-MM-DD.json`），导出即得全部已登录账号的完整凭证数组。文件顶层是数组，每个元素关键字段：

```jsonc
[
  {
    "access_token": "eyJhbGciOi...",      // RS256 JWT，CN 有效期约 60 天，INTL 约 365 天
    "refresh_token": "eyJhbGciOi...",     // 一次性使用，续签即轮换
    "domain": "www.workbuddy.cn",         // 关键：域名决定 region 归组
    "nickname": "浮陀",
    "uid": "0de0a237-1a6e-...",           // 即 userId，X-User-Id 头必需
    "profile_raw": { "preferred_username": "..." },
    "needs_relogin": true                  // 工具自记的「刷新失败」标记（见 §6 实测：网关可复活）
  }
]
```

**域名 → region 分组表（实测 2026-09-18）**：

| domain 后缀 | 归组 | 网关实际调用的端点 |
| :--- | :--- | :--- |
| `*.cn`（www.workbuddy.cn / www.codebuddy.cn） | **CN**（provider `workbuddy`） | `https://copilot.tencent.com/v2/chat/completions` 等 |
| `*.ai`（www.workbuddy.ai / www.codebuddy.ai） | **INTL**（provider `workbuddy-intl`） | `https://www.codebuddy.ai/v2/chat/completions` 等 |

> workbuddy.ai 与 codebuddy.ai 为同一 realm（JWT 签名 kid 相同），凭证互通；`.cn` 与 `.ai` 两 realm **不互通**，所以必须分组。

### 4.2 途径 B：CLI 登录抓取

安装 CodeBuddy CLI 并登录，从其本地配置（`product.json` 默认端点 + 登录态）提取 token；适合单账号。

### 4.3 途径 C：控制台手动录入

控制台 → 账号管理 → 对应提供商组「新增账号」，逐字段填 userId / accessToken / refreshToken。适合临时补账号。

## 5. 配置中转

v3.0.9 起，导入 API 与控制台对话框**原生识别 wb-switch 导出格式**（数组每项均含 `access_token` + `domain` + `uid` 即命中），自动按域名分组为 `workbuddy`（CN）与 `workbuddy-intl`（INTL）两个提供商，账号 ID 取用户名 slug。

### 5.1 方式 A：粘贴 wb-switch 导出全文（推荐）

1. 登录控制台 → **账号管理** → **批量导入**。
2. 选「粘贴文本」（或「上传文件」直接选 `.json`），把导出文件**全文**贴入。
3. 冲突策略：**首次导入选什么都行**；重复导入同一文件务必选 **跳过**（原因见下方注意）。
4. 点「开始导入」。识别成功时结果区会显示 **「wb-switch 格式已自动分组」** 徽标与说明条。

**注意（重要）**：导入后网关首次续签（手动 `/admin/api/refresh` 或运行期 401 自动续签或定时保活）会**轮换 refresh token 并写回 SQLite**——导出文件里的旧 refresh token 随之作废。因此：

- 同一份旧导出文件**不要**再以「覆盖」策略重复导入（会把 DB 里的新 token 覆盖回已失效的旧 token）；
- 导入一次后，**SQLite 数据库就是唯一凭证事实源**，请把 `db/custom.db` 纳入备份。

### 5.2 方式 B：手动构造 providers JSON 粘贴

适用于想要自定义 provider id / 账号 id 的场景：

```json
[
  {
    "id": "workbuddy",
    "type": "workbuddy",
    "name": "WorkBuddy 腾讯代码助手（CN）",
    "config": { "region": "cn" },
    "accounts": [
      { "id": "my-account-1", "name": "账号一（www.workbuddy.cn）",
        "userId": "0de0a237-…", "accessToken": "eyJ…", "refreshToken": "eyJ…" }
    ]
  },
  {
    "id": "workbuddy-intl",
    "type": "workbuddy",
    "name": "WorkBuddy 国际站（INTL）",
    "config": { "region": "intl" },
    "accounts": [
      { "id": "intl-1", "name": "账号二（www.codebuddy.ai）",
        "userId": "d504e0fb-…", "accessToken": "eyJ…", "refreshToken": "eyJ…" }
    ]
  }
]
```

字段说明：`type` 必须是 `workbuddy`；`config.region` 为 `"cn"`（默认）或 `"intl"`，决定整组端点；账号内联字段 `userId` / `accessToken` / `refreshToken` 即三件套。

### 5.3 方式 C：CSV（仅单提供商追加）

四列 `name,userId,accessToken,refreshToken`，首行可表头；导入时需选择目标提供商（CSV 无法携带 region 信息）。

### 5.4 方式 D：管理 API 直调（自动化脚本）

```bash
# 登录取会话令牌
TOKEN=$(curl -s -X POST http://127.0.0.1:18787/api/console/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<你的密码>"}' \
  | sed 's/.*"sessionToken":"\([^"]*\)".*/\1/')

# wb-switch 文件全文作为 text 字段导入
jq -Rs '{text: ., conflict: "skip"}' wb-switch-accounts-2026-09-14.json \
| curl -s -X POST http://127.0.0.1:18787/api/console/accounts/import \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" -d @-

# 响应含 "format":"wb-switch-accounts" 与逐行 results
```

### 5.5 导入后立即续签（激活账号池）

```bash
curl -s -X POST http://127.0.0.1:18787/admin/api/refresh \
  -H "Authorization: Bearer <master_key>"
```

成功标准：返回 `{"success":true,"results":[{"provider":"workbuddy","refreshed":true,"count":N},…]}`；控制台「账号管理」各账号行出现「最近刷新」时间。之后 token 保活由定时任务自动进行（§10.2）。

## 7. 模型路由配置

路由表定义「客户端模型名 → 有序候选链」，候选顺序即故障转移优先级。WorkBuddy 常用原生模型：`deepseek-v4.1-flash`、`deepseek-v4-pro`、`deepseek-v4-flash`、`glm-5.2`、`kimi-k3-1`。

### 7.1 控制台 UI

「模型路由」→「新增路由」：模型名填客户端将使用的名字；候选逐行添加（提供商下拉选 `workbuddy` / `workbuddy-intl`，模型下拉列原生模型，可手动输入）；候选行可拖拽排序、启停。

### 7.2 本指南实测使用的 6 条路由

| 客户端模型 | 候选链（按优先级） |
| :--- | :--- |
| `deepseek-v4.1-flash` | workbuddy/deepseek-v4.1-flash → workbuddy/deepseek-v4-pro → workbuddy/deepseek-v4-flash |
| `deepseek-v4-pro` | workbuddy/deepseek-v4-pro → workbuddy/deepseek-v4.1-flash |
| `deepseek-v4-flash` | workbuddy/deepseek-v4-flash → workbuddy/deepseek-v4.1-flash |
| `glm-5.2` | workbuddy/glm-5.2 |
| `kimi-k3-1` | workbuddy/kimi-k3-1 |
| `glm-5.2-intl` | workbuddy-intl/glm-5.2（INTL 链路） |

```bash
# API 方式创建（会话鉴权同 §5.4）
curl -s -X POST http://127.0.0.1:18787/api/console/routes \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -d '{"model":"deepseek-v4.1-flash","candidates":[
        {"providerId":"workbuddy","model":"deepseek-v4.1-flash"},
        {"providerId":"workbuddy","model":"deepseek-v4-pro"}]}'
```

> 代码内 `DEFAULT_ROUTES` 提供了含 openrouter 兜底的候选链作内存回填（DB 无该路由时生效）；生产建议显式落库（本文 6 条即落库形态）。

## 8. 客户端接入

### 8.1 Claude Code（Anthropic 协议）

```bash
export ANTHROPIC_BASE_URL=http://127.0.0.1:18787
export ANTHROPIC_API_KEY=sk-uag-xxxxxxxx          # 控制台「虚拟密钥」
claude
# /model glm-5.2   （或路由表中的任意模型名）
```

Claude Code 每次请求自带 system 前缀，天然规避 INTL 站 11128 拦截（§12.1）。

### 8.2 任意 OpenAI 客户端

`base_url = http://127.0.0.1:18787/v1`，`api_key = sk-uag-…`，模型名填路由表模型（如 `deepseek-v4.1-flash`）。

### 8.3 curl 速验

```bash
# OpenAI 协议（注意：WorkBuddy 为 forceStream 提供商，非流式请求也会收到 SSE 透传，§12.4）
curl -N http://127.0.0.1:18787/v1/chat/completions \
  -H "Authorization: Bearer sk-uag-…" -H "Content-Type: application/json" \
  -d '{"model":"deepseek-v4.1-flash","max_tokens":100,
       "messages":[{"role":"system","content":"You are a helpful assistant."},
                   {"role":"user","content":"你好"}]}'

# Anthropic 协议（流式）
curl -N http://127.0.0.1:18787/v1/messages \
  -H "x-api-key: sk-uag-…" -H "anthropic-version: 2023-06-01" \
  -d '{"model":"glm-5.2","max_tokens":100,"stream":true,
       "messages":[{"role":"user","content":"只回答四个字：协议测试"}]}'
```

```bash
# 7. 机器可读状态（Agent-Native）
curl $GW/admin/api/status -H "Authorization: Bearer $MK"

# 8. 控制台人工核验：账号管理（余额/刷新时间/签到列）、运行日志（账号归属 + token 数 + 失败原因）
```

## 10. 运维手册

### 10.1 进程与端口

- 开发：`pnpm run dev`（热重载）；生产：`pnpm run build && pnpm start`（默认 18787，`PORT=` 覆盖）。
- 端口冲突显式报 `EADDRINUSE`，不会静默换端口。
- 常驻：systemd / launchd / Docker 三模板见 `README.md`「常驻部署」；Docker 注意把 `./db` 挂为卷。

### 10.2 定时任务（签到 + Token 保活）

控制台「定时任务」配置 cron 与时区；到点对全部 workbuddy 账号执行每日签到与 token 刷新（`onSchedule` 钩子）。手动触发：`/admin/api/checkin`、`/admin/api/refresh`。

### 10.3 账号冷却与恢复

- 触发 429 / 403 / 风控业务码（11128 等）→ 账号进入指数退避冷却（1→2→4→8 分钟封顶），**SQLite 持久化，重启不丢**；
- 冷却期间请求自动漂移到下一健康账号；成功请求自动清零冷却；
- 控制台「账号管理」冷却列实时显示剩余时间。

### 10.4 日志与审计

- 「运行日志」七维筛选（模型 / 提供商 / 账号 / 密钥 / 状态码 / 用量来源 / 时间范围含自定义起止），失败原因落库（v3.0.8 起）；
- 「导出 CSV」按当前筛选导出（BOM + RFC 4180，Excel 直接打开）；
- 滚动窗口 5000 条；`/admin/api/status` 的 `usage_daily` 输出近 7 天按日聚合（不受窗口截断）。

### 10.5 备份与迁移

- **冷备**：停进程后复制 `db/custom.db`（单文件含全部配置与凭据，妥善保管！）。
- **逻辑导出**：控制台「账号管理 → 导出」：完整导出（含凭据，可再导入闭环）/ 脱敏导出（分享用，系统拒绝其再导入）。
- **v2.4.0 迁移**：设置页「KV 迁移工具」。

### 10.6 代理（可选）

控制台「设置 → 全局代理」：http/https/socks5/socks5h、代理池限流轮换、绕过列表、出口 IP 实测按钮；提供商级覆盖（`proxyOverride`）。WorkBuddy INTL 若需代理出海，给 `workbuddy-intl` 单独配置覆盖即可，不影响 CN 直连。

## 11. 安全模型

| 层 | 机制 |
| :--- | :--- |
| 客户端鉴权 | 虚拟密钥（`sk-uag-` 前缀）多把并存：模型白名单 / 启停 / 角色；Bearer 与 `x-api-key` 双头支持 |
| 管理鉴权 | `master_key`（全量 `/admin/api/*`）；timingSafeEqual 常量时间比较 |
| 定时任务 | `cron_secret` 降权密钥（只触发签到/保活，不能改配置） |
| 控制台会话 | 双通道：HttpOnly Cookie（SameSite=Lax）+ Bearer 令牌兜底（iframe 跨站丢 Cookie 场景自动切换）；登录爆破 5 次锁 15 分钟 |
| 凭据展示 | 界面一律掩码；保存时未改动字段服务端回填原值——**任何一次保存都不可能把凭据清空** |
| 导出脱敏 | 脱敏导出被导入 API 识别并拒收 |
| 单文件风险 | `db/custom.db` 含全部上游凭据明文——请用文件权限 / 磁盘加密保护 |

## 12. 常见问题 FAQ

### 12.1 INTL 请求报 11128 "first message is not system prompt"

WorkBuddy 国际站（`.ai` 域）WAF 要求请求**首条消息必须是 system**。CN 站无此要求。

- Claude Code 等自带 system 前缀的客户端天然满足；
- 裸 curl / 简单聊天客户端请给消息列表加一条 `{"role":"system","content":"…"}`；
- 网关侧已按设计处理该码：触发即账号冷却 1 分钟 + 自动故障转移到下一账号/候选（实测 §6 #9/#10）。

### 12.2 源文件标记 needs_relogin 的账号能导入吗？

**能（实测 4/4 全部复活）**。切换器工具的刷新协议失败 ≠ refresh token 真失效：网关续签走 `POST /v2/plugin/auth/token/refresh` + `X-Refresh-Token` 头 + 正确 Origin/UA，实测对标记账号全部成功。导入后跑一次 `/admin/api/refresh` 即可验证。

### 12.3 重复导入同一份导出文件会怎样？

- 「跳过」策略：幂等安全（账号已存在即跳过）；
- **「覆盖」策略：危险**——若网关已续签轮换过 token，旧文件里的 token 已失效，覆盖导入会把失效 token 写回 DB。导入一次后请以 DB 为准，勿再覆盖。

### 12.4 客户端没请求 stream 却收到 SSE？

WorkBuddy 是 `forceStream` 提供商（上游非流式 JSON 可能是 200 业务错误包，强制流式才能可靠区分）。**非流式请求也会收到 SSE 透传**——这是等价保留自原版的设计行为，非 bug。OpenAI 客户端一般都能处理；如需严格 JSON，选非 forceStream 提供商（openai/anthropic 兼容类）。

### 12.5 token 会过期吗？

- CN access token ≈ 60 天，INTL ≈ 365 天；refresh token CN ≈ 90 天、INTL ≈ 365 天；
- 网关在 401 时自动无感续签 + 定时保活任务每日刷新，正常运维下无需人工干预；
- 长期离线（超过 refresh 有效期）后需重新登录源工具导出新文件再导入。

### 12.6 会话粘性是怎么工作的？

有 `x-session-id` / `x-conversation-id` 头或稳定 system+tools 指纹时，同一会话固定打同一健康账号（保上游前缀缓存热）；无粘性键时纯轮询；账号冷却时照常漂移。客户端无需配置。

### 12.7 怎么加更多账号 / 提供商？

- 同一 region 加账号：账号管理对相应组「新增」或再次导入（skip 策略幂等）；
- 新增其他类型中转：API 中转 → 新增（提供商 ID 下拉含 3 类原生预设与自定义 ID；openrouter 等按类型填 BaseURL/Key）。

### 12.8 端口改了之后客户端连不上？

控制台与网关 API **同端口**。改 `PORT` 后客户端的 base_url 同步改；Docker 记得改映射。网关从不监听第二个端口。
